## 1. 再分析結果: 弱点3点の検証

前回候補3点（期待値の未明示／規律の省略防止不足／判断の線引き曖昧）を
method.md 本文と突き合わせて再検証した。**3点とも実在を確認**。該当箇所は以下。

### 弱点1: 期待値の未明示（何をどこまでやれば合格か書かれていない）

Fableは行間を埋められるが、Opus/Sonnetは「書いていないこと」を実行しない。

| 該当箇所 | 問題 |
|---|---|
| §1「ゴールを一文で言語化する」 | 言語化した文を**どこに出すか**（報告に含める？頭の中だけ？）、書けなかったら**どうするか**が未指定。下位モデルは黙って着手する |
| §3-5「保存済みの基準データとの完全一致で確認」 | 基準データの**置き場所・形式の規約がない**。「なければ作って残す」も、どこに残すか不明なため実行されない |
| §3-7「記録」/ §7「記録の省略」 | 記録の**書き出し先が未指定**（コミットメッセージ？別ファイル？）。下位モデルはチャット返信に書いて終わり、次セッションに残らない |
| §6「基準データを育てる」 | 同上。場所・命名の既定がない |

### 弱点2: 規律の省略防止不足（省略への歯止めがない）

| 該当箇所 | 問題 |
|---|---|
| 末尾「全部を毎回やる必要はない」 | 逃げ道が広すぎる。下位モデルはこの一文を根拠に規律全体を省略する。「コア5原理は例外なく」とあるが、5原理は抽象度が高く「適用したつもり」で素通りできる |
| 完了報告の直前に**強制ゲートがない** | §5に報告の規律はあるが、報告を書く前に自分を検査する具体的手順（チェックリスト）がない。Fableは内面化しているが、下位モデルには明文のゲートが要る |
| §7 アンチパターン | 記述が「失敗の説明」形式で、**実行中に発火するトリガーがない**。読んだ時は理解するが、作業中に想起されない |

### 弱点3: 判断の線引き曖昧（判断語が定義されていない）

| 該当箇所 | 問題 |
|---|---|
| §2「可逆は進み、不可逆は確認」 | 境界例が未列挙。git push（自動デプロイ直結）、共有ドキュメントへの書き込み、外部への通知送信などを下位モデルは誤分類する |
| §2「実務的に最適な方を選び」 | 「実務的に最適」が無定義。既定則（逸脱最小の方を選ぶ等）がない |
| §5「質問は自分で潰せないものだけ」 | 「調べれば分かる」と「人間の判断が必要」の境界が判断依存。具体例リストがない |
| §6「隣接する改善は提案、完遂に必要な発見は直す」 | この2つの**区別基準が書かれていない**。下位モデルが最も誤る箇所（勝手に直す／必要な修正まで提案止まり、の両方向に振れる） |

### 補足所見（軽微・任意）

- SKILL.md は発火時に読まれるが、method.md の再読導線は「適用の仕方」の1段落のみ。
  長時間タスクの中盤でコンテキストから抜け落ちた規律を呼び戻す仕組みが弱い。
  最重要ゲート（完了前セルフチェック）を SKILL.md 側にも1行置くことで緩和する（案6）。

## 2. 加筆修正案（承認後に適用）

方針: **追記は外科的に最小限**。文書の肥大は下位モデルの保持力をさらに下げるため、
「新規セクション1つ＋既存箇所への短い挿入6件」に絞る。

### 案1 [弱点1] §1 ゴール言語化に出力先と失敗時の動きを追加

```diff
 **ゴールを一文で言語化する。** 「何ができたら完了か」を自分の言葉で書けないなら、
 理解が足りていない。受け入れ条件が指示に書かれていればそれを正とする。
+言語化したゴールは着手宣言（最初の報告）に含めて人間の目に触れさせる。
+一文で書けない場合は着手せず、何が不明かを質問する。
```

### 案2 [弱点1] §3-5/§6 に記録・基準データの置き場所の既定を追加

§3-7「記録」の末尾に追加:

```diff
 7. **記録** — 「事象→根本原因→対応→実測値(before/after)」の形式で残す。
    これで将来の自分や別のモデルが同じ調査を繰り返さずに済む。
+   置き場所の既定: 対象コードと同じリポジトリのgit管理下
+   （コミットメッセージ、またはスクリプト隣のREADME/docs）。
+   基準データはスクリプトと同ディレクトリの baseline/ 等に保存する。
+   チャット返信だけに書いて終わらせない。それは次のセッションに残らない。
```

### 案3 [弱点3] §2 可逆判断に境界例の表を追加

§2「判断に迷ったら〜」の4項目の直後に追加:

```diff
+境界例の分類（迷いやすいもの）:
+
+| 操作 | 分類 | 動き |
+|---|---|---|
+| ローカル編集・ローカルcommit・テスト実行・一時ファイル作成 | 可逆 | 進めて報告 |
+| git push（自動デプロイに直結する場合を含む） | 対外的 | その先が確立された運用範囲なら進める。初めての接続先なら確認 |
+| 共有ドキュメント・外部DB・外部サービスへの書き込み | 対外的 | 既存運用の範囲内か確認。テスト書き込みは対象と件数を明示 |
+| 削除・DROP・force push・既存データの上書き | 不可逆 | 事前確認＋バックアップ。例外なし |
```

### 案4 [弱点3] §5 質問の線引きに具体例を追加

```diff
 **質問は「自分で潰せないもの」だけに絞る。** 調べれば分かること、慣習的な
 デフォルトがあることは、自分で決めて報告に明記する。人間の判断が本当に必要な
 分岐だけを、選択肢＋推奨＋理由の形で一度に聞く。小出しの質問は相手の時間を奪う。
+自分で決めて報告する例: 既存パターン踏襲の実装選択、命名、一時ファイルの置き場、
+検証方法の選定。聞く例: 費用・契約が発生する、公開範囲が変わる、データを消す、
+要件同士が矛盾している、受け入れ条件そのものが不明。
```

### 案5 [弱点3] §6 隣接改善と必要修正の区別基準を追加

```diff
 **頼まれたことをやる。** 要求されていない機能・抽象化・防御コードを足さない。
 隣接する改善に気づいたら、勝手にやらず一度だけ提案する。
 一方で、頼まれたことの完遂に必要な発見（バグ、設計上の欠陥）は遠慮なく直しに行く。
+区別基準: 放置すると今回の成果物が正しく動かない・壊れる欠陥 → 直して報告に明記。
+動くが品質・保守性・将来の問題 → 一度だけ提案して判断を仰ぐ。迷ったら提案側に倒す。
```

### 案6 [弱点2] 新セクション §8「完了前セルフチェック」＋逃げ道の閉鎖

method.md 末尾の「適用の仕方」の前に新設:

```markdown
## 8. 完了前セルフチェック（省略不可）

完了報告を書く前に、以下の5問に自答する。全てYesでなければ「完了」と書かない。

1. 実際に動かして出力を自分の目で見たか（ビルド成功・型チェック通過は含まない）
2. 変更した理由（根本原因）を一文で言えるか
3. 既存の正常系が壊れていないことを確認したか
4. 未検証の点・残課題・指示からの逸脱を報告に列挙したか
5. 不可逆・対外的な操作を無断でやっていないか

Noがある項目は、ごまかさずに「未完了」「未検証」「人間待ち」として報告に明示する。
```

「適用の仕方」の修正:

```diff
 タスク開始時に §1、行き詰まったら §3、外部システムに触るなら §4、
 人間に何か聞きたくなったら §5 を読み返す。
-全部を毎回やる必要はない。ただし**コア5原理だけは例外なく適用する**。
+全部を毎回やる必要はない。ただし**コア5原理と§8の完了前セルフチェックは
+例外なく適用する**。省略してよいのは「読み返す量」であって「原理の適用」ではない。
```

SKILL.md のコア原理5の直後に1行追加（発火時に必ず目に入る位置）:

```diff
 5. **読者のために書く**: 報告は結論先出し。過程を見ていなかった人が一読で状況を掴める文章にする。失敗・逸脱・限界は正直に書く。
+
+完了報告の前に method.md §8 の5問セルフチェックを通すこと（省略不可）。
```

## 3. CLAUDE.md モデル分業セクション改稿案（承認後に適用）

現行は「メインがFableのとき（現行デフォルト）」が先頭。既定を Opus/Sonnet に反転する。

```markdown
## モデル分業（advisor / worker サブエージェント）

コスト最適化のための分業。定義は `~/.claude/agents/advisor.md` / `worker.md`。

- **メインがOpus/Sonnetのとき（現行デフォルト）**：fable-method を常時適用し、
  完了報告前に method.md §8 のセルフチェックを必ず通す。
  複雑タスクの方針判断・設計の壁打ち・行き詰まりの打開では `advisor`（Fable）を
  タスクあたり概ね1回呼んでよい。サブエージェントはコールドスタートなので、
  promptに目的・現状・試したこと・選択肢・関連パスを全て含める。
- **メインがFableのとき**：トークン消費の大きい作業（複数ファイル調査、Web調査、
  ログ解析、定型的な一括編集）は `worker`（Sonnet）に委譲してよい。事前確認不要。
  設計判断・方針決定・最終レビューはメイン（Fable）が持つ。
  独立サブ課題は並列ワーカー可、ただし細分化しすぎない。advisor は呼ばない。
- 単純タスク（1ファイル修正、質問応答）はサブエージェントを使わずメインが直接やる。
- **検証**：デプロイや納品物など要件が列挙できる成果物は、`verifier`（Haiku）に
  合格基準リストを渡して独立チェックさせてよい（実行者と別モデルで検証する）。
  事前確認不要。設計判断や深いコードレビューはverifierに投げない。
- **Opus昇格が必要な項目（未実装・記録のみ）**：D-1 hookによる規律の物理強制層
  （settings.json / hooks 実装）は今回スコープ外とした。導入するか否かの設計判断は
  Opus以上のメインで行う。
```

変更点の要約: (1) Opus/Sonnet節を先頭・既定に、(2) fable-method常時適用＋§8ゲートを明記、
(3) 共通ルール（単純タスクは直接）を独立行に、(4) D-1のOpus昇格項目を末尾に記録。
