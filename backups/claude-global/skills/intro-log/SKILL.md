# intro-log

新しい道具を採り入れたときに、後から「なぜ入れたのか」「何のリスクがあるのか」を思い出せる形で1件ずつ記録するスキル。目的は、導入を場当たりで終わらせず、判断の履歴を資産に変えること。

溜まった記録は2つの用途を持つ。(1) `tool-inventory` の棚卸し台帳への入力、(2) 人に教えるときの実例集。だから「記録すること自体」に意味がある。

## いつ使うか

- 新しいツール・MCP・API連携・サードパーティサービスを導入したとき
- 自作のloop/skill/agent/hook/goalを新しく作ったとき
- 既存の仕組みを別のものに置き換えたとき(旧記録に「置き換えた」と追記)
- ユーザーが「記録して」「ログに残して」と明示したとき

## 手順

### 1. 対話で埋める

以下の項目を、ユーザーに聞きながら、あるいは会話の文脈から拾って埋める。**一度に全部聞かない** — 会話履歴から分かるものは先に埋め、足りないものだけを最小限の質問で確認する。特に「解決したい問題」と「失敗時に壊れるもの」の2つは重要なので、空欄なら必ず聞く。

| 項目 | 内容 | 補足 |
|---|---|---|
| 名称 | ツール/手法名 | |
| 日付 | 導入日(YYYY-MM-DD) | `user_time` などで現在日を取得 |
| レベル分類 | L0〜L5のどこに属するか | 定義は同ディレクトリの levels.md を参照 |
| 6分類 | loop/skill/agent/goal/hook/MCP のどれか | 迷ったら理由と共に仮置き |
| 解決したい問題 | なぜ入れたか | **必須。**「なんとなく」なら導入自体を疑う |
| 権限の範囲 | 何を読める/書けるか | 読み取り専用か書き込み可か |
| 失敗時に壊れるもの | ブラスト半径 | **必須。**「特にない」なら安全度が高い証拠 |
| 後日評価 | 定着した/使っていない/置き換えた | 導入時は空欄。3週間後などに追記 |

### 2. レコードを出力して追記する

導入記録ファイル(既定: `~/.claude/intro-log.md`、なければユーザーに保存先を確認)に、以下の形式で1件を**追記**する(既存を上書きしない)。

```markdown
## 導入記録: [名称]
- 日付: YYYY-MM-DD
- レベル分類: L?
- 6分類: loop / skill / agent / goal / hook / MCP のいずれか
- 解決したい問題: 
- 権限の範囲: 
- 失敗時に壊れるもの: 
- 後日評価: (未評価)
```

ファイルにアクセスできない環境では、レコードをそのままチャットに出力し、「これを `~/.claude/intro-log.md` に追記してください」と伝える。

### 3. 棚卸しへの橋渡しを促す

記録したら、そのツールが `tool-inventory` の台帳にまだ無ければ「棚卸し表にも1行足しておきましょうか」と一度促す。記録と台帳が二重管理にならないよう、intro-logは「時系列の日記」、tool-inventoryは「現在の一覧」という役割分担を保つ。

### 4. 後日評価のリマインド(任意)

導入から3週間後などに「定着したか」を見直せると、使っていないものを外す判断につながる。ユーザーが希望すれば、リマインダー作成を提案してよい(`reminder_create` など)。押し付けはしない。

## 原則

- **「解決したい問題」が書けない導入は、導入自体を疑う。** 目的の言語化ができないものは、たいてい不要か、まだ作業単位が大きすぎる。
- **1件ずつ、その場で。** 溜めてまとめて書こうとすると、結局書かずに場当たりに戻る。導入した瞬間に1件、が鉄則。
- **記録は将来の自分と、教える相手のためのもの。** 「なぜこれを入れたか」を未来の自分が読んで分かる粒度で書く。それがそのまま人に教えるときの実例になる。
- **後日評価まで書いて1件が完成する。** 導入時の記録は半分。3週間後の「定着/未使用/置換」が入って、初めて判断の履歴として機能する。
